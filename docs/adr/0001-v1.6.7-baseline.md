# ADR-0001: v1.6.7を開発基準とする

* Status: Accepted
* Target: LhaForge v1.7.x
* Related:

  * ADR-0002: v1系外部DLL互換を維持する
  * ADR-0003: x64本体とLegacyHostを採用する
  * ADR-0004: Built-in BackendをFallbackとして持つ

## Context

LhaForgeには、v1系とv2系で大きく異なる設計思想が存在する。

LhaForge v1.xは、統合アーカイバプロジェクトの外部DLLを利用する方式を中心としており、ユーザーによるDLLの更新・差し替え、LFCaldixによるDLL取得、B2E対応、複数のLegacy Format対応などを特徴としている。

一方、LhaForge v2ではArchive Backendが内蔵化され、64bit専用化、外部DLL依存の廃止など、内部構造が大きく再設計されている。

LhaForge v1.7.xで目指すものは、v2の設計をv1のUIへ移植することではない。

目的は、

> LhaForge v1.xのUI、操作性、外部DLL文化、Legacy Compatibilityを可能な限り維持したまま、現代のWindows環境に適合させること

である。

そのため、v1系の最終版であるLhaForge v1.6.7を直接の開発基準とする必要がある。

## Source Verification

v1.7.xの開発開始前に、次の2つを比較した。

* LhaForge公式サイトで配布されていたv1.6.7ソースアーカイブ

  * `lfsrc_1_6_7.tgz`
* GitHubリポジトリ

  * Tag: `ver_1_6_7`
  * Commit: `3917887`

比較結果:

```text
公式配布ソース:          235 files
Git側との共通ファイル:   235 files
内容が異なるファイル:      0
公式配布側のみ:             0
Git側のみ:                   2
```

Git側だけに存在したファイル:

```text
README.md
LhaForge/Thumbs.db
```

共通する235ファイルについて、内容差分は確認されなかった。

そのため、GitHubの`ver_1_6_7`タグは、公式配布されたLhaForge v1.6.7ソースコードと実質的に同一の開発基準として利用可能と判断した。

## Decision

LhaForge v1.7.xは、GitHubの次のCommitを直接の開発基準とする。

```text
Tag:
ver_1_6_7

Commit:
3917887

Commit message:
Ver.1.6.7
```

v1.7.xの開発ブランチは、このCommitから直接分岐する。

初期開発ブランチ:

```text
main-osamix
```

Git履歴上は次の関係を維持する。

```text
LhaForge original history
        │
        ↓
3917887
ver_1_6_7
        │
        ↓
main-osamix
        │
        ↓
LhaForge v1.7.x development
```

`ver_1_6_7`タグ自体は変更・移動しない。

v1.7.xで行ったすべての変更は、

```text
ver_1_6_7..main-osamix
```

の差分として追跡可能な状態を維持する。

## Development Principle

v1.6.7を基準とすることは、v1.6.7の実装をすべて無条件に維持することを意味しない。

維持対象は主に次の通りとする。

* v1系のUI・操作性
* 外部アーカイバDLLとの互換性
* Legacy Formatへの対応
* MenuEditor等のv1系User-facing component
* LFCaldix / cldxを含むLegacy DLL運用文化
* 既存ユーザー環境からのMigration可能性
* v1系設定・関連付け・Shell Integrationとの互換性

一方で、次のような内部実装は現代化する。

* x64対応
* Unicode処理
* Windows API
* DLL Load Security
* Path Security
* Logging
* Error Handling
* DPI対応
* Build System
* Installer / Updater / Uninstaller
* Archive Backend abstraction
* Security validation
* Modern Windows compatibility

つまり、

```text
v1.6.7の挙動・思想
        +
現代的な内部実装
        =
LhaForge v1.7.x
```

を基本方針とする。

## Relationship with LhaForge v2

LhaForge v2は、参考実装およびModernizationの情報源として利用する。

特に次のような項目について、v2の実装を調査・参考にすることを許容する。

* セキュリティ修正
* Unicode対応
* Windows互換性
* Archive format handling
* Library update
* Bug fix
* UI改善
* Build環境改善

ただし、v2のArchitectureそのものをv1.7.xへ移植することは目的としない。

v2から機能や修正を取り込む場合も、

> v1.7.xの設計思想に適合する形へ再設計して導入する

ことを原則とする。

## Legacy Baseline

v1.6.7の仕様は、ソースコードだけでなく実際のインストール環境も含めてLegacy Baselineとして記録する。

調査対象には少なくとも次を含む。

```text
LhaForge.exe
MenuEditor.exe
Unregister.exe
LFAssist.exe
LFAssist64.exe
LFCaldix.exe
ShellExtDLL.dll
ShellExtDLL64.dll
lficons.dll
b2e32.dll
b2e32.txt
LhaForgeHelp.chm
ReadMe.txt
epuninst.exe
```

また、Runtimeで生成・取得される次の要素も対象とする。

```text
LhaForge.ini
LFCaldix.ini
cldx\
External Archive DLL
Registry
File Association
Shell Extension registration
Temporary files
```

Baselineでは、可能な限り次の情報を記録する。

* 誰が生成するか
* 誰が読み込むか
* 誰が更新するか
* ユーザーによる変更が想定されているか
* Installer管理対象か
* Migration対象か
* Repair対象か
* Uninstall対象か

## Evidence Policy

Legacy仕様を判断する際は、推測だけで確定しない。

Evidenceとして次を利用する。

```text
Source Code
Official Website
Official Forum
Official Release Archive
Clean Install Snapshot
Post-DLL-Download Snapshot
Runtime Test
```

各設計資料では、必要に応じて確度を記録する。

例:

```text
Confirmed
High
Medium
TBD
```

不明な仕様については、実装前に無理に確定させず`TBD`として残す。

## Repository Policy

v1.6.7の原コードは、v1.7.x開発開始直後に大規模な整理・移動を行わない。

まず、

```text
Legacy Baseline
Ownership Matrix
Migration Design
Architecture Design
ADR
```

を作成し、設計が確定してからBuild ModernizationおよびSource Refactoringを開始する。

これにより、

> どの変更が単なるRepository整理で、どの変更が実際の挙動変更なのか

をGit履歴上でも追跡しやすくする。

## Official Source Archive

公式配布された`lfsrc_1_6_7.tgz`は、開発用ソースそのものとしては使用せず、Legacy Evidenceとして保存する。

役割は次のように分ける。

```text
Git tag ver_1_6_7
    開発Baseline

lfsrc_1_6_7.tgz
    公式配布物としてのEvidence
```

これにより、Git履歴を維持しながら、公式配布ソースとの一致も将来再検証できる。

## Consequences

### Positive

* 原作者のGit履歴をそのまま維持できる
* v1.6.7からの変更内容を明確に追跡できる
* v1系のUI・互換性・運用思想を維持できる
* v1.6.7ユーザーからのMigration設計を行いやすい
* v2とは異なる目的を明確化できる
* Legacy仕様とModernizationの境界を整理できる
* 将来的なRegression調査が容易になる

### Negative

* 古い設計やコードを理解しながらModernizationする必要がある
* v2を直接ベースにする場合よりLegacy Compatibilityの負担が大きい
* 古いBuild設定・API・依存関係を段階的に整理する必要がある
* Legacy Formatや外部DLLなど、現代的なApplicationでは通常不要な互換層を維持する必要がある

## Alternatives Considered

### LhaForge v2をベースにv1風UIを実装する

採用しない。

v2ではArchive Backendや外部DLL互換など、v1系の主要Architectureが大きく変更されている。

v1系Legacy Compatibilityを後から再構築するより、v1.6.7をModernizeする方が目的に適している。

### 新規にLhaForge互換Applicationを作成する

採用しない。

UIや機能を再現できても、LhaForge v1.xのGit履歴・挙動・設計との連続性が失われる。

### 公式配布`lfsrc_1_6_7.tgz`を新規Repositoryへ展開して開発する

採用しない。

公式ソースそのものは正しいが、GitHubの`ver_1_6_7`とソース内容が一致することを確認済みである。

Gitタグから分岐する方が原作者の開発履歴を維持できる。

### GitHub masterをそのまま開発基準とする

採用しない。

masterはv1.6.7以降の別世代の開発を含む可能性があり、v1系Modernizationの明確なBaselineにならない。

## Notes

このADRは、

> LhaForge v1.7.xは何を継承し、何を現代化するApplicationなのか

というプロジェクト全体の出発点を定義する。

今後の設計判断で迷った場合、

> その変更はv1系の価値を維持しながら現代化するものか

を判断基準の一つとする。

ただし、互換性のために安全性・安定性・保守性を犠牲にすることはしない。

安全性上必要な変更については、Legacy Behaviorとの差異を文書化した上でModernizationを優先する。
